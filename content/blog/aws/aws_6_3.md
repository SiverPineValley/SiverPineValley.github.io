## 6-3-1) RDS Backups

- 자동화된 백업
	- **매일 데이터베이스 전체 백업 (backup window 동안)**
	- 트랜잭션 로그는 **RDS에 의해 매 5분 마다 자동으로 백업**됨.
	- 어느 시점이든 복구할 수 있음 (가장 오래된 시점부터 5분 전 까지)
	- **1~35일의 보유 기간**. 0으로 설정 시 자동 백업이 비활성화됨.
- 수동 DB 스냅샷
	- 수동으로 유저에 의해 트리거되며, 원하는 만큼 보유할 수 있음
- 정지된 RDS 데이터베이스는 여전히 비용을 지불할 것이다. 만약, 오랜 기간 정지시킬 경우 스냅샷 화 및 복구하는 것이 훨씬 저렴할 것이다.

</br>

## 6-3-2) Aurora Backups

- 자동화된 백업
	- 1~35일의 보유 기간 (비활성화 불가능)
	- 타임 프레임 내의 특정 시점으로 복구 가능
- 수동 DB 스냅샷
	- 수동으로 유저에 의해 트리거되며, 원하는 만큼 보유할 수 있음

</br>

## 6-3-3) RDS & Aurora 복구 옵션

- RDS / Aurora 백업 복구 혹은 스냅샷을 통해 새로운 데이터베이스 복구
- **S3로부터 MySQL RDS 데이터베이스를 복구**
	- On-premises 데이터베이스의 백업 생성
	- 이를 Amazon S3에 저장 (Object Storage)
	- 백업 파일을 새로운 RDS 인스턴스에서 복구
- **S3로부터 MySQL Aurora 클러스터 복구**
	- Percona XtraBackup을 사용하여 On-premises 데이터베이스 백업 생성
	- 이를 Amazon S3에 저장
	- 백업 파일을 새로운 Aurora Cluster에서 복구

</br>

## 6-3-4) Aurora Database Cloning

- 데이터의 장기 백업 보관을 지원하고, 자동 복제본을 통해 재해 발생 시 빠르게 데이터 복구를 가능하게 하는 데 가장 효과적이기 때문에 사용된다.
- **존재하는 Aurora DB Cluster에서 새로운 Aurora DB Cluster 생성**
- 스냅샷 생성 및 복구보다 빠르다.
- `copy-on-write`  프로토콜을 사용한다.
	- 최초로, 새로운 DB 클러스터는 기존 DB 클러스터와 같은 볼륨을 사용한다. (카피가 없으므로 빠르고 효율적이다.)
	- 새로운 DB 클로스터로의 업데이트가 끝나면, 추가 스토리지가 할당되고 데이터가 카피되며 이후 분리된다.
- 매우 빠르고 비용 효율적이다.
- **운영 DB에 영향을 주지 않고 검증용 DB를 생성할 때 유용**하다.
